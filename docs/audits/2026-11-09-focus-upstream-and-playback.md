## 视频为什么会在打开时切线路

在 API 31 x86_64 模拟器运行公开 Focus 389 包，登录态和原有数据保持不变。首次启动的首页曾出现 `api.bilibili.com` 域名解析失败；点击重试后推荐流正常加载，所以这次网络启动错误不能直接归因于播放器。随后从推荐页打开两条不同视频：两次日志都显示首帧出现前自动从 `upos-sz-mirrorcosov.bilivideo.com` 切到 `upos-hz-mirrorakam.akamaized.net`。第二次的时间线为：05:06:30.983 点击、05:06:31.183 建立播放器、05:06:34.531 记录 `first_frame_timeout` 回退、05:06:35.000 开始创建视频解码器；切线后视频能够播放。本地截图在 `.local/focus-video-audit-*.png`，含登录页面与推荐内容，不发布到仓库。

模拟器设置页显示「CDN 设置：基础URL」，并非手动固定 COSOV 线路。当前 [`VideoPlaybackViewModel.kt`](../../app/src/main/java/com/android/purebilibili/feature/video/viewmodel/VideoPlaybackViewModel.kt) 用 2,500 毫秒判断首次播放是否 `STATE_READY`。它的 `usesCdnRewrite` 实际上只判断选中 URL 与备用 URL 是否不同，普通服务器下发的主、备用线路也会启动这条短计时；即使只有音频备用 URL 不同，也会进入同一路径。回退时播放器重设媒体源，并清空自适应 DASH 描述。这解释了为何切线会增加一次播放器准备过程。另一个待修点是播放器错误同时由 ViewModel 和页面状态监听器处理，可能在同一错误上连续切两次。

上游 `6fff91ff8` 仍使用相同的 2,500 毫秒和 `STATE_READY` 条件，也仍有第二个错误监听入口。上游后续确实增加了非 PCDN 候选优先、风险线路过滤、弱网详情调度、播放恢复等改进；这些改进要在同步时吸收，但不能声称仅合并上游就能消除本次复现的短计时问题。当前两条样本说明“过早切线”真实发生，尚不能据此量化所有网络和视频上的平均首帧时长，也不能断定 COSOV 在所有地区都慢。

## 这轮播放器修复验证到了什么

在 `codex/focus-sync-20261109` 分支，短计时只对用户指定主机、自定义规则或地区规则确实改写了视频 URL 的线路生效。普通服务器签发的主、备用 URL 即使不同，也不再因此触发 2,500 毫秒回退；播放器仍可在明确的媒体错误、缺失音轨时换线。首帧迟迟不出现且前向缓冲为零时，原有 10 秒卡顿恢复现在也能覆盖首次播放，并且只尝试尚未用过的候选。页面监听器在 500 毫秒后处理同一错误前，会先确认播放器仍持有该错误，避免与 ViewModel 的恢复动作重复切线。

用本机 JDK 21、仓库已有的 `.local/miuix` 源码运行三组定向测试，合计 30 个测试通过、0 失败；`assembleDev`、R8 和 Dev 安装也通过。最初构建被 GitHub Packages 的 Miuix 401 与终端 JDK 17 阻断，改用本地源码和已安装的 JDK 21 后通过；这两项是环境问题，不是业务测试失败。API 31 x86_64 模拟器安装的 Dev 包为 `com.android.purebilibili.focus.dev`，与原登录版分开存放数据。

在 Dev 包中打开 `BV1JsK5eyEuB`，没有再看到 `first_frame_timeout`；主线路随后返回 HTTP 错误，播放器记录 `player_error` 并换至 Akamai 备用线路，画面实际播放。旧版 Focus 389 打开同一视频时仍记录 `first_frame_timeout`，约 2,500 毫秒后换线。Dev 包再次进入该视频时，日志明确记录 HTTP 567，最终仍显示播放画面。两次打开的缓存、登录和网络状态不同，因此这些记录证明短计时误触发已消失、真实错误回退仍存在，不能证明首帧平均耗时降低。

默认安装只启用投屏插件，`CDN 智能选线` 插件默认关闭；它的历史线路评分不会为普通默认播放排序。HTTP 567 的具体服务端原因尚未查明，不能把它写成 COSOV 在所有网络都不可用。后续同步播放器与 CDN 时，需要在不改写签名 URL 的前提下验证上游候选排序、错误后的线路记忆和不同网络下的首帧时间，才能处理用户所说的“频繁手动切线路”。本轮没有完成这项跨网络验证。

## 下一步怎样同步并验证

1. 在独立分支保护当前 Focus 发布基线。先合入 `v0.7.8` 并按模块解决冲突：构建与数据模型、播放器与 CDN、首页与导航、动态与关注分组、设置与更新、最后迁移测试。随后合入至 `upstream/main`，对新出现的冲突重复语义检查。
2. 逐项保护上一轮登记的 Focus 能力：独立包名与更新源、Room 旧数据迁移、顶部标签实际显示结果、关注分组与五档排序、动态过滤、搜索三段显隐、相关推荐显隐、历史清空入口显隐。原始基线与实现位置见 [上次同步审计](2026-09-23-focus-upstream-sync.md#必须保护的-focus-功能基线)。上游已有同类能力时使用上游实现，并迁移用户原有配置与画面。
   上游 `v0.7.0` 已加入「大家都在搜／搜索历史／搜索发现」三段显隐，并在新版 `SearchScreen` 使用 `getSearchLandingSectionVisible(context, 0..2)`；这与 Focus 的三项搜索降噪能力重叠。同步时应以这套上游界面和配置为唯一入口，把 Focus 旧值算成升级前实际显示状态后迁入，避免同时保留两套开关。搜索历史的“记录数据”设置与“显示区块”设置用途不同，不能合并成一个开关。
3. 本轮已修复短计时误触发与同一错误的重复回退，并完成定向测试和 API 31 播放对照。继续测试首帧、Seek、自动/手动线路、不同编码、不同网络和 HTTP 567 的处理；不能只凭视频最终能播放宣布“打开缓慢”已解决。
4. 上游当前测试源码错误要修复并跑通 `PerfGuard`、`Correctness`；之后再做 Dev、Release、签名连续性、旧版覆盖升级与 Focus 特色功能回归。上轮完整设备测试仍有 63 项中的 16 失败、3 跳过，不能挪用上一轮部分定向通过结果。
5. 在正式发布前锁定上游提交，使用高于 389 的 Focus 版本码和官方版本名加 `.focus.1` 的命名，保留稳定 Focus 更新渠道，并让受保护标签直接触发构建，核对 APK 摘要、签名证书与构建证明的 tag ref。此次调查阶段不创建新 Release，也不修改现有客户端更新源。

第 1、2、4、5 项仍是后续同步与发布工作；这轮没有合并上游或创建新 Release。
