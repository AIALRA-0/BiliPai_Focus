# 视频卡片性能与开合动效复查

日期：2026-10-29。范围：首页卡片进入详情、自动返回、预测返回及中断接管。

初次复查读取四份性能文档、归档统计与脚本，并核对工作区源码（含上一轮未提交的修改）。下方“动效发现”保留修改前的判断；后续实现见文末。两阶段均未编译、运行 Gradle 测试、重新解析原始 trace 或采集新的逐帧画面。以下区分归档事实、源码推导与视觉建议。

## 性能文档结论

- 归档 `manifest.json` 的 40 个文件均存在，大小与 SHA-256 全部一致；这验证归档完整性，不等于重新验证所有 SQL 或测量结论。
- 两个进入样本的归档 JSON 与报告中的主帧最大值、布局最大值、RT 中位数一致；其主线程 TID 为 19152、RT TID 为 20614，分别映射到各自 trace 的不同 UTID。
- 开关模糊均存在同量级重布局和 RT 工作，不能把关闭模糊当成修复，也不能把单对样本差值作为模糊的精确开销。第一轮 FrameTimeline 的实际呈现间隔与后续 atrace 的线程耗时属于不同口径。
- 延后正文、加载许可、Surface 延续、延后像素读回及背景缓存的实现方向与文档索引一致。它们尚无修改后测量结果；正文挂载、像素读回和 Surface 释放仍可能将负担移至落位后。
- 基线报告中的“未修改源码”等语句描述历史采集阶段，不描述当前工作区。README 已说明报告为历史副本。

### 脚本复用限制

`analyze_clean.py` 写死 `/tmp/bilipai-card-perf/trace_processor`、TID 19152/20614，并选取首个 OPENING 与首个 HELD；`compare_return.py` 同样写死执行器路径与 PID 19152。当前归档样本与线程号相符，未发现因此导致的表格错误，但它们不能直接用于重启进程后的新采集。复用时应参数化执行器与目标进程，按同一进程和同一次会话配对相位；无匹配或有多个候选时显式报错。

## 动效发现（修改前）

| 当前行为 | 建议 | 原因 |
| --- | --- | --- |
| 自动飞行与手势分别计算姿态；无手势时清空 `lastFollowPose` | 新抓取先冻结当前可见的完整姿态，再承接拖动 | 保留深度不代表旋转、透视、缩放与枢轴也连续 |
| 竖向卡片圆角先增大再归零；横卡采用单调 smoothstep | 先对比竖向卡片的小幅鼓胀与单调插值方案，保留屏幕空间圆角补偿 | 可减少展开中段的形状变化；属于视觉取舍，未证实为卡顿根因 |
| 自动返回已用贝塞尔；部分注释仍说“返回 Linear” | 明确导航主路径与兼容 sharedBounds 策略的区别 | 避免误把已缓动的深度再次缓动，或同时调整两套时钟 |
| 媒体交接窗口用几何进度 0.82–0.98 定义 | 记录对应时间比例，调曲线时联动检查交接 | 几何进度不是时间进度；单改曲线会改变封面、标题和背景接管节奏 |

### P2：自动飞行切入手势的姿态锚点不完整

定位：`MiuixVideoCardNavTransition.kt` 的 `followPose`（约 614–636 行）与 `transformEntry`（约 868–903 行）。

无手势时 `followPose` 将 `lastFollowPose` 重置为默认值，随后图层独立采用 `resolveMiuixVideoCardClickTransform`。新手势则从 `lastFollowPose` 取 `followAnchorPose`，没有继承此前实际显示的点击姿态。

源码反例：取 morph=0.5、来源卡横向偏移为 -0.5，自动姿态的 Z 旋转为 +1.6°、缩放为 0.975、cameraDistance 为 5.5；首个手势事件若 progress=0、触点尚未移动，跟随姿态从默认锚点得到 0°、1、8。即使 morph 不跳，姿态通道也有不连续的条件。X/Y 旋转与枢轴也需一起承接。实际系统是否允许在特定入场时刻抓取、视觉跳变幅度如何，尚未通过运行确认。

建议优先保存自动阶段实际应用的完整姿态，在新手势首帧作为锚点；处理枢轴变化时应保持可见变换一致。既有取消恢复再抓取的锚点逻辑需要保留，不能每帧重新认领锚点。该发现针对可中断性，不宣称普通完整开合必然跳变。

### 圆角：保留补偿，评估竖向卡片的鼓胀

定位：同文件 `resolveMiuixVideoCardGestureCornerPx`（约 187–209 行）及物理圆角除以两轴缩放的代码（约 944–954 行）。

当前已经修正了非等比缩放造成圆角变椭圆的问题；这部分应保留。横卡还用当前短边的一半约束半径，不能简单换成固定 `RoundedCornerShape`。

竖向卡片采用线性端点半径加正弦鼓胀。以来源 16dp、浮动半径 32dp、全屏 0dp 为例，morph 为 0、0.25、0.5、0.75、1 时，函数输出约为 16、26.14、32、23.80、0dp。这里是补偿外层非等比缩放前的目标半径，额外姿态缩放与透视还会影响最终画面。浮动半径还取设备圆角与 28dp 的较大值。

这不属于已证实的错误：中段圆角增大可以表达悬浮。但它比横卡多一轮形状变化。优先比较较小鼓胀与横卡式单调插值，并统一有限尺寸下的半径约束；保持来源落点半径、全屏矩形端点、正反向同深度取值一致。手机、大屏和窄分屏分别看，不能直接用设备物理圆角决定所有窗口的视觉圆角。

### 曲线和媒体交接：先澄清坐标，再调整观感

定位：`VideoSharedTransitionPolicy.kt` 的 `VideoHeroMotionSpec`、`VideoCardReturnTimeline.kt` 的媒体窗口，以及 `resolveVideoHeroNavMotion`。

导航主路径的自动进入与返回均使用 `(0.24, 0.60, 0.32, 1)`，返回时长为进入的 0.83 倍并受 220ms 下限约束；几何与窗口自适应还会调整实际时长。手势拖动不应再套自动曲线。启用 `matchReleaseVelocity` 的松手补间由 `NavVelocityHandoffEasing` 接管，实际并不使用声明的空间贝塞尔，因此仅修改 `returnSpatialSpec` 不会统一改变所有返回场景。

以未叠加几何调整的 360ms 进入、299ms 自动返回为例，通过贝塞尔参数求逆得到：

| 返回几何进度 | 时间比例 | 自动返回约耗时 |
| --- | ---: | ---: |
| 0.55 | 22.68% | 68ms |
| 0.82 | 42.25% | 126ms |
| 0.98 | 76.27% | 228ms |

0.82–0.98 的封面/标题交接约占 102ms，之后约 71ms 仍有最后 2% 的几何位移。这只是函数计算，不是实际呈现帧或新的性能结果；手势释放的速度交接曲线不可套用此表。整卡位图返回的 alpha 另用 0.55–0.98，不能把它与 live → 封面的窗口混为一谈。

因此当前不建议直接换成更强的 ease-out：它可能进一步把交接挤到前段并拉长小位移尾段。先解决中断姿态，再按同一深度检查封面、正文、背景清晰度和圆角；如仍有拖尾感，再成组调整自动返回曲线与交接窗口。不要把所有用户时长设置强行压到 300ms。

## 初次审查结论

**中断连续性：暂不通过（Block），先修复自动姿态到手势姿态的接管。** 这是源码可构造的不连续条件，尚无运行复现。完整开合的曲线、圆角是否更好看，需要逐帧视觉依据，不能凭公式宣布优化完成。

建议功能顺序：完整姿态锚点 → 竖向卡片圆角方案比较 → 返回交接窗口与曲线协同 → 落位后正文挂载和整卡捕获错峰。所有共用变化覆盖玻璃、MD3、Miuix；不借用玻璃专属参数修改原生布局。减少动态效果当前会关闭整卡 morph，应继续保留。

## 后续实现进度

已根据用户确认实施：

- 自动图层记录实际应用的姿态对象和枢轴，新手势从这份姿态建立一次性锚点；常规自动帧不额外转换姿态对象。坐标事件尚未到达时继续保留自动姿态。
- 带旋转或缩放的中断姿态保持原枢轴；关闭手势位移时也不重新选择触点枢轴。透视、缩放与旋转的安全区间包含接手时的值，避免自动透视和释放冲量被首帧钳制。
- STACKED 整卡采用与横卡相同的单调 smoothstep 圆角；来源 16dp、全屏 0dp 时，中点为 8dp。COVER_ONLY 保留悬浮圆角，但同样受当前短边一半约束。两轴缩放补偿保留。
- 澄清景深恒等映射注释。自动贝塞尔、时长、手势释放曲线与封面/标题交接窗口保留，后续可单独继续优化返回尾段节奏。

新增回归用例位于 `VideoCardGestureFollowStateTest.kt` 与 `MiuixVideoCardNavTransitionTest.kt`，覆盖自动飞行三个深度的新抓取、位移开关、延迟坐标、锚点清理、超出跟随区间的已有姿态，以及多尺寸、多圆角下的整卡单调收敛。原有取消后再抓取用例继续保留。已核对源码接线与 Git 差异，未运行这些用例，不能据此宣布运行时跳变或性能卡顿已消除。

材质边界：修改位于玻璃、MD3、Miuix 共用的导航图层，不改变材质布局参数；减少动态效果仍由现有策略关闭整卡 morph。未增加帧循环或异步任务。

### 返回尾段节奏实现

后续继续调整自动返回曲线为 `(0.24, 0.60, 0.58, 1)`，进入和取消恢复保留原曲线。总时长、速度设置、几何自适应、预测拖动的线性映射与松手释放速度接续不变。兼容 sharedBounds 的显式非交互返回也使用同一自动返回曲线；其默认交互返回仍为 Linear。

按贝塞尔函数求逆，在未叠加几何调整的 299ms 自动返回中：

| 几何事件 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 整卡位图开始接管（0.55） | 68ms | 87ms |
| 封面/标题开始接管（0.82） | 126ms | 160ms |
| 媒体及整卡交接完成（0.98） | 228ms | 251ms |
| 交接完成至落位 | 71ms | 48ms |

此表仅是函数计算，不能表示实际呈现耗时或提速。几何窗口保持不变，因此拖动、反向和松手时不会因切换时间映射而改变封面/标题的 ownership。整卡位图的 0.55–0.98 窗口已迁入 `VideoCardTransitionVisualTimeline`，由公共函数统一计算 smoothstep alpha，原完成边界和关闭跟随时的端点行为保留。

新增用例约束自动返回的单调无过冲、时间后半段媒体交接、交接窗口长度、尾段时间比例、封面与标题同步、整卡反向恢复，以及导航自动返回/取消分支的曲线接线。用例尚未运行；已完成源码和差异核对。后续功能可继续处理落位后正文挂载与整卡捕获的错峰，当前没有修改这两类工作的执行时机。

### 落位后整卡捕获错峰实现

原捕获任务在 HELD 后等待两个帧边界，与详情侧正文后两个帧边界放行播放器的逻辑独立，可能同帧启动。现在 `VideoCardPixelOwner` 持有当次点击的单向许可；详情侧正文就绪且 Playback → Comments → Related 首轮许可依次放行后，等待两个帧边界，再发布该许可。来源捕获等待许可后再经过原有两个帧边界读回。正文、播放器和评论不等待捕获完成，没有固定毫秒延时，也不在等待许可时持续请求帧。

首页 `VideoCard` 与通用 `VideoCardNativeSnapshot` 两个捕获入口均已接入。许可只认 entry 创建时记住的点击对象，不按相同 BVID/来源键重新认领；发布前还检查当前活跃归属。普通关闭卡片过渡的入口不启动许可等待帧。返回、换卡、后台、失焦和来源销毁仍撤销旧捕获；取消返回不复活任务。数据迟到时继续等正文就绪，失败时不为可选整卡快照抢占首屏，返回沿现有封面/文字 fallback。

这里的“首轮完成”只表示本地挂载许可已依次放行并留出绘制机会，不代表网络、解码、播放器异步准备或 GPU 全部空闲。新用例覆盖长时间未放行、同键不同点击不能互相放行、放行后的绘制间隔及等待期间返回后不复活；原有后台、失焦、读回中取消用例保留。仅完成源码和差异核对，未编译、运行用例或测量新的性能数据。

### 单独检查：关闭卡片过渡后的普通导航

此阶段仅检查，没有修改普通导航曲线、圆角或错峰策略。视频详情 entry 在 MIUIX 模式下采用 `NavTransitions.MiuixDefault`：顶页横向位移、来源页四分之一宽视差及 alpha 衰减；圆角与遮罩由 NavDisplayEffects 独立承担。不能将整卡返回曲线或来源卡圆角直接套入。

发现：`shouldDeferVideoDetailLoadUntilEntryTransitionFinished` 允许普通导航等待该 entry 落位，但 `rememberVideoDetailEntryWorkPhase` 的 `staggerWork` 仍受卡片 `transitionEnabled` 控制。关闭卡片后其阶段直接为 Related，导航落位时媒体、评论、推荐可能一起放行。后续应将“是否有导航入场、是否首次挂载、是否复用迷你播放器”的工作许可与卡片材质动画开关解耦，保留已加载父详情和取消返回的锁存，再评估是否需要调整普通 Miuix 动效本身。

### 普通导航工作调度实现

已将上述错峰条件改为 `shouldStaggerVideoDetailEntryWork`：依赖 entry 首次加载是否延后及是否复用迷你播放器，移除卡片 `transitionEnabled` 条件。普通导航持有 navigation scope 时同样延后首次加载，因此关闭卡片动画也会在落位、正文就绪后，按两个帧边界一组依次放行播放准备、评论和推荐。仅控制现有许可的启动时机，不保证异步任务结束；普通 Miuix 曲线、位移和圆角未改。

entry 工作阶段继续单向锁存，不因返回预览、换集或重组重置。手动遮挡等导致 effect 取消后，从当前阶段继续，只为尚未放行的阶段等待帧；已进入 Related 的父详情不重播准备过程。迷你播放器复用及不需要延后加载的直接入口保持直接放行。该调度共用于玻璃、MD3、Miuix，没有材质参数或窗口尺寸阈值。

新增回归用例覆盖卡片关闭时普通导航仍错峰、复用与直接入口豁免、Playback/Comments 阶段恢复、完成后返回不重放。仅源码与差异检查，未编译、运行用例或采集修改后性能数据。

### 展开、关闭时的圆角来源（调整前记录）

- 带标题、UP 信息的 STACKED/SIDE_BY_SIDE 整卡：来源为点击时 `AppShapes.containerCornerDp(ContainerLevel.Card)` 对应的实际卡片圆角，按 morph 的 smoothstep 收敛到全屏 0，再在关闭时恢复来源值；不采用设备圆角作为中段半径。
- COVER_ONLY：保留悬浮圆角，中段参考 `max(28dp, 设备圆角, 来源圆角)`，并受当前短边一半约束。
- 普通 Miuix 滑页：宿主独立读取设备报告的圆角，MIUIX 默认裁切前导边；无系统半径时该路径的默认值为 0。其他要求全角裁切的样式才会在缺少报告时回退到 32dp。
- 整卡 morph 活跃时关闭宿主设备圆角裁切，避免再叠一层不同半径。外壳仍保留两轴缩放补偿；截图的实际安装包版本和渲染路径不能仅从静态图片判定。

设备圆角来自系统 WindowInsets RoundedCorner 或系统资源，并非测量屏幕得到的几何真值，也不保证不同厂商报告完全一致。

### 按用户偏好采用设备圆角

最新实现取代前述来源圆角收敛方案：STACKED、SIDE_BY_SIDE、COVER_ONLY 的悬浮阶段统一采用系统报告的设备圆角，不再以 28dp 作为设备值下限。导航宿主没有系统报告时保留现有 32dp 回退；直接调用转场且未提供有效设备值时才使用局部回退。

半径由来源卡片 → 设备圆角 → 全屏边界分两段 smoothstep 插值，0、0.5、1 深度分别对应三个端点，正反向同深度取值相同；各段端点斜率为零。实际绘制保留短边一半上限与两轴缩放补偿。整卡活跃期间仍关闭宿主重复圆角裁切。此处仅改变卡片外壳几何，普通 Miuix 导航的工作调度、曲线和其他材质参数保持当前实现。

本轮最早修改前，双列/仅封面入口中段采用 `max(28dp, 设备圆角, 来源圆角)`，横向整卡单独使用来源圆角。随后曾将双列改为来源圆角收敛，现按用户明确偏好改为上述统一设备策略。已更新小于 28dp 的设备值、布局一致性、正反向和窄窗口裁切用例；未编译或运行用例。
